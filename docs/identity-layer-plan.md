# План реализации `src/identity/` (P0/P1 — без изменения поведения)

Основание: архитектурный аудит FVM (карта N1–N8, D1–D9, ошибки E1–E10, гипотезы H1–H6). Решения владельца: PR #6 не объединять; точечные правки алиасов/дедупликации прекращены; SQLite, Shadow V3, grading и исторические ключи логов не менять; формулы, пороги VALUE/NEAR/WAIT и расчёт вероятностей не менять; рабочий код не менять до анализа диагностики.

## 0. Цели и не-цели

**Цель:** один модуль, в котором живут нормализация названий, реестр клубов, сопоставление provider ID и определение «тот же матч». Старые модули делегируют ему; наблюдаемое поведение FVM остаётся **бит-в-бит прежним**.

**Не-цели первого этапа:** объединение двух таблиц алиасов (меняет поведение — E3), запись в SQLite, изменение ключей `snapshotKey`, перевод V3/grading на новую модель чтения, дедупликация при приёме данных. Всё это — отдельные этапы с решением владельца (раздел 6).

**Правило против цикла регрессий:** один PR на **этап**, а не на симптом. Любой новый алиас/дедупликация вне плана блокируется; кандидаты в алиасы приходят только из `identity-census` (доказательство по данным) и вносятся пакетом с одобрением владельца.

## 1. Что должно быть в `src/identity/`

```
src/identity/
  normalize.js    normalizeName(raw)                    — ровно текущая canonicalTeamName (L146 teamAliases.js)
  legacy.js       legacyCanonicalLocalHistory(raw)      — текущая localHistory.canonical (N2)
                  legacyCanonicalContext(raw)           — текущая contextIds.canonical (N3)
                  legacyCanonicalDiscovery(raw)         — текущая discovery.canonical (N5)
                  (адаптеры нужны, чтобы старые потребители получили ИДЕНТИЧНЫЕ ключи, пока таблицы не объединены)
  registry.js     ClubRegistry — неизменяемый реестр, строится из seed (TEAM_ALIAS_GROUPS + CLUB_ALIASES + расширения contextIds)
                  clubId(name)           → строка = текущий canonicalTeamIdentity(name)   (на этапе 1 ID выводится, не хранится)
                  searchKeys(name)       → то же, что teamSearchAliases → canonicalTeamName
                  evidence(name)         → то же, что teamIdentityEvidence
  resolve.js      resolveClub(name, {provider, providerId, competition})
                    → { clubId, via: "NORMALIZED" | "ALIAS" | "PROVIDER_ID", providerId } | null
                  на этапе 1 путь PROVIDER_ID работает только в теневом режиме (см. §3), результат в production не используется
  match.js        sameClub(a, b)         ≡ sameTeamIdentity
                  sameClubForOdds(a, b)  ≡ clubNameSimilarity(a, b) >= 0.85  (clubMatching.js переиспользует реестр)
                  sameMatch(rowA, rowB)  ≡ логика logicalMatch.js (после решения по PR #6; до этого — как dedupeLogicalMatches в e7e133c)
  parity.js       теневой компаратор legacy ↔ identity (флаг FVM_IDENTITY_PARITY=1), пишет расхождения в data/diagnostics/identity-parity.jsonl; никогда не бросает исключений и не меняет результат
  index.js        единственная точка импорта
```

Принципы API: функции чистые и детерминированные; неоднозначность → `null` (никогда не угадывать); никакого ввода-вывода внутри (seed передаётся при создании); тип данных `clubId` — строка, формат закреплён тестами.

## 2. Реестр клубов и сопоставление provider ID

### 2.1 Модель данных (в памяти, из seed-файла; SQLite не меняется)
```
Club        { clubId, canonicalName, names: [{ name, norm, source, evidence }], providerIds: [{ provider, providerTeamId, evidence }] }
ProviderId  UNIQUE (provider, providerTeamId) → ровно один clubId
```
Seed-файл `src/identity/seed.json` создаётся **генерацией** из текущих таблиц (скрипт + тест, что результат эквивалентен текущему поведению), а не вручную.

### 2.2 Порядок разрешения клуба
1. `(provider, providerTeamId)` — точное совпадение в реестре (самый сильный сигнал);
2. курируемый алиас (текущие группы);
3. нормализованное имя (`normalizeName`), если оно единственное в реестре;
4. иначе `null` → в очередь `identity_unresolved` (файл диагностики), модель получает «нет данных», а не угаданный клуб.

На этапе 1 **в production используются только пункты 2–3** (поведение = сегодняшнему). Пункт 1 считается параллельно (теневой режим) и сравнивается с именным результатом.

### 2.3 Как наполняется соответствие provider ID (без записи в SQLite)
Скрипт `scripts/baseline/provider-id-map.mjs` (будет добавлен на этапе S4) читает SQLite readOnly: для каждого `(source, homeTeamId|awayTeamId)` собирает множество написаний; формирует отчёт:
- `ID → несколько идентичностей` (конфликт: один id у двух клубов — потенциальная ошибка провайдера или алиаса);
- `идентичность → несколько ID у одного провайдера` (например, переименование/дубль клуба);
- `ID без имени` и `имя без ID` (строки без team id — E5).
Решение о внесении пары в реестр принимает владелец по отчёту (доказательство: ≥N матчей с совпадением счёта/времени/стороны — как в `identity-census`).

## 3. Теневой режим и гарантия совместимости

`resolveClub` с `provider/providerId` работает **параллельно** старому пути и сравнивается с ним через `parity.js`. Расхождение — не ошибка прода, а запись в `identity-parity.jsonl` для анализа: «ID говорит A, имя говорит B». Только после анализа владелец решает, включать ли ID-путь как основной.

Откат любого этапа — `git revert` одного PR; новые модули изолированы, потребители переключаются поштучно.

### Ворота совместимости (подробности — `docs/baseline-kit.md`)
- **G1** `identity-legacy-snapshot.json` на реальном корпусе: дайджесты всех секций совпадают побитно (ключи, классы эквивалентности, пары для коэффициентов, выравнивание контекста).
- **G2** `replay-drift` на замороженной SQLite: 1X2 каждого логированного прогноза расходится ≤ 1e-9 между «до» и «после».

- **G4** `npm test` на Node 22 — полностью зелёный.

## 5. Тесты первого этапа (полная совместимость)

Каталог `test/identity/` (создаётся на S1; файлы названы по назначению):

1. `legacy-parity.test.js` — для **каждого** имени реального корпуса (`test/fixtures/identity-corpus.json`, только названия, лиги, источники, счётчики — после одобрения владельца) `identity.normalizeName == canonicalTeamName`, `clubId == canonicalTeamIdentity`, `searchKeys == teamSearchAliases→canonicalTeamName`; для всех пар внутри лиги `sameClub == sameTeamIdentity`, `sameClubForOdds == (clubNameSimilarity>=0.85)`; выравнивание контекста совпадает с `alignContextTeamIds`. Золото = `identity-legacy-snapshot.json`, снятый на Termux.
2. `legacy-adapters.test.js` — `legacyCanonical*` совпадают с `canonical` старых модулей на корпусе (пока модули не удалены) и на тестовых строках с диакритикой, `&`/`and`, цифрами, кириллицей.
3. `registry-invariants.test.js` — нет канонического ключа у двух клубов; нет алиаса, объединяющего клубы разных стран (по `country` из seed); все пары из seed симметричны и транзитивны; seed воспроизводим генерацией.

5. `key-builders.test.js` — 6 копий `kickoff|home|away` дают одинаковые ключи с единым построителем; старые `snapshotKey` в фикстуре логов находятся без изменений (ключи immutable-логов не меняются).
6. `no-behavior-change.replay.test.js` — на анонимизированном наборе фикстур (из baseline) λ, вероятности Form/Team Strength/консенсуса, Agreement, Stability, DQ, категория идентичны золотым значениям.
