## 3. Гипотеза о тройном учёте домашнего преимущества

### 3.1 Структура формулы (`models.js:77–83`)
`λ_home = L · (homeGF/hG / L) · (awayGA/aG / L) · 1.08`, где `L` — среднее число голов на команду за матч **по всем** играм лиги. Для «среднего» матча домашние голы лиги `L_h` и гостевые `L_a` связаны с `L = (L_h + L_a)/2`, поэтому:
- домашняя атака, нормированная на `L`, уже содержит множитель `L_h/L` (> 1);
- гостевая защита (пропущенные в гостях = голы хозяев), нормированная на `L`, содержит тот же `L_h/L`;
- сверху — явный `1.08`.
Итого для лиги с `L_h = 1.54`, `L_a = 1.22`: `λ_home ≈ L_h²/L · 1.08 ≈ 1.54²/1.38 · 1.08 = 1.86`, `λ_away ≈ L_a²/L · 0.92 ≈ 0.99` (факт 1.54 и 1.22). То есть **структурно гипотеза верна: домашнее преимущество входит в атаку, в защиту и в явный множитель**.

### 3.3 Вывод
- Гипотеза **корректна для компонента Team Strength**: усреднённые λ смещены (дом +14 %, гости −19 %), а исправление нормировки улучшает LogLoss самого компонента (−0.028 без сглаживания, −0.004 при k = 8).
- Для **Production** (consensus с Form) это неважно или даже вредно: убрать множители при k = 8 — LogLoss 1.0269 против 1.0253 (хуже на 0.0016), в новом сезоне 1.0302 против 1.0254; Form смещён в противоположную сторону и частично компенсирует Team Strength. При k = 8 сглаживание к общему среднему само уменьшает смещение (λ 1.65/1.13).
- **Множители менять не нужно**: нет доказанного выигрыша для Production, и они в любом случае перестанут играть роль, когда нормировка будет корректной в рейтинговой модели. Независимая проверка, если вы захотите её провести: Shadow-вариант «k = 8 + множители 1.0/0.95» против «k = 8» на ≥ 1 500 новых матчей, критерий — парная разность LogLoss с нижней границей ДИ, исключающей ухудшение, и калибровка средней вероятности хозяев по лигам.

## 4. Проект рейтинговой модели `ratings-v1` (только Shadow)

Не дублирует Challenger и «Shadow k = 8»: те работают с таблицей текущего сезона и не учитывают силу соперников и прошлые сезоны.

### 4.1 Модель
- Состояние: для каждой пары (лига, команда) — рейтинг атаки `a` и защиты `d`; для лиги — базовый уровень голов `μ` и домашнее преимущество `h` (обучаются онлайн).
- Ожидаемые голы: `λ_home = exp(μ + h + a_home − d_away)`, `λ_away = exp(μ + a_away − d_home)`.
- Обновление после каждого завершённого матча — шаг градиента логарифмической правдоподобности Пуассона: `a_home += η(x − λ_home)`, `d_away −= η(x − λ_home)` и аналогично для гостей; увеличенный шаг для команд с малым числом матчей, слабая L2-регуляризация. Рейтинги обновляются **с учётом силы соперника** автоматически (ожидание зависит от соперника).
- Смена сезона: все рейтинги домножаются на коэффициент переноса `κ` (в экспериментах 0.5–1.0), новые/вышедшие команды начинают с нуля.
- Исходы: распределение счёта Пуассона с поправкой Диксона–Коулза (параметр ρ) → 1X2. Вторая голова: Elo по разнице мячей + упорядоченная логит-модель ничьей. Итог — среднее двух голов (при желании среднее с V2H как с независимой по природе моделью; в моих проверках «DC + Elo + V2H»).
- Гиперпараметры (η, κ, регуляризация, ρ, ширина зоны ничьей) подбираются **только по LogLoss на закрытом обучающем окне** и замораживаются под номером версии до следующего планового пересмотра (раз в месяц).

### 4.2 Хронологическая безопасность
1. Состояние на момент `asOf` строится только из матчей со статусом «завершён», у которых `kickoff < asOf` и время получения результата `fetchedAt ≤ asOf` (для живого режима; при исторической проверке — `kickoff`). Поздно подгруженные «старые» матчи не меняют уже выданные прогнозы.
2. Каждая запись содержит `stateAsOf`, номер версии гиперпараметров, число матчей и контрольную сумму списка использованных матчей: прогноз можно воспроизвести бит-в-бит.
3. Тест на утечку: добавление в историю матча с `kickoff ≥ asOf` не меняет прогноз; перестановка порядка загрузки не меняет прогноз; повторный запуск идемпотентен.
4. Результат матча модель получает только после старта и только через общий механизм сопоставления результатов (`resolveHistoryMatch`, тип совпадения сохраняется).

### 4.3 Интеграция без дублирования
- Отдельный Shadow-модуль со своим файлом записей; не импортирует `analyse.js`, не меняет категорию, Edge, EV, VALUE, Telegram, не пишет в чужие файлы; отказ или исключение глотаются и логируются, флаг отключения.
- Запись: `type: RATINGS_SHADOW_PREDICTION`, тот же `snapshotKey`, что у `dual-shadow` (по этому ключу сопоставляются Production, Challenger, V2H, «Shadow k = 8» и рыночная запись); поля: вероятности 1X2, λ, значения обеих голов, глубина истории (игр у обеих команд, число сезонов), `paramsId`, `stateAsOf`, `matchesHash`.
- Оценка — единый скрипт, читающий уже существующие `SHADOW_RESULT` и `SHADOW_MARKET_BENCHMARK`.
- Необходимое условие для всех выводов о рынке: запись настоящего закрытия за 5–10 минут до старта и (желательно) нескольких сезонов исторических коэффициентов.

### 4.4 Что не входит в первую версию
Составы, травмы, xG, календарь (эффект отдыха не подтверждён), связь между лигами через Лигу чемпионов (вторая очередь), рынки OU/AH/BTTS (матрица счёта сохраняется, но не оценивается).

### Этап 2. Сравнение с рынком (нужны реальные закрывающие коэффициенты)
- Выборка ≥ 3 000 матчей с настоящим закрытием; метрики: парный LogLoss против рынка, вес модели `b₂` в регрессии исход ~ рынок + модель, CLV.
- Критерий: нижняя граница ДИ `b₂` > 0 на двух независимых периодах и в ≥ 2 группах лиг.
- Ожидаемый исход по текущим данным: **не проходит** (разрыв 0.04 LogLoss, `b₂` ≈ 0). Прогресс возможен от многолетней истории (абляции: без прошлого сезона хуже на 0.02–0.025) и новых признаков.

### Этап 3. Отбор VALUE (только если пройден этап 2)
- Метрика: избыток над ожиданием «рынок честный», CLV, калибровка выбранной стороны, наклон c. Критерий: избыток > 0 с нижней границей ДИ > 0 в большинстве временных блоков.
- Если этап 2 не пройден, модель используется как улучшенная базовая вероятность для мониторинга, но не как основание для VALUE.

### Этап 4. Устойчивость
По лигам, ранний/поздний сезон, новые команды, хозяева/гости, диапазоны коэффициентов, разбиение на независимые периоды без перекрытия. Число проверяемых вариантов ограничено заранее, множественные сравнения учитываются.
