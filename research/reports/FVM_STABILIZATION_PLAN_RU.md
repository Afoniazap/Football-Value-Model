## 1. Цепочка «матч → VALUE/NEAR» и карта блокировок [ФАКТ-КОД]

Порядок в `src/app.js:269-345`:
`buildModel` → `classify` → `applyMarketFreshnessGuard` → DQ v2 → `calculateRisk` → `runSanityChecks` → `buildShadowComparison` → `applyShadowDisagreementGate` → запись `signals/official-signals`.

| Проверка | Файл | Действие | Статус |
|---|---|---|---|
| Модель есть и **legacy DQ ≥ 65** (`item.dataQuality`, не DQ v2) | `decision/classify.js:5` | → WAIT | **Блокирует** |
| Есть коэффициенты (`bestH2H`) | `classify.js:13` | → WAIT | **Блокирует** |
| Edge ≥ 4 пп **и** EV ≥ 4 % **и** Confidence ≥ 70 | `classify.js:50` | иначе NEAR/REJECTED | **Блокирует** |
| Рынок STALE (15–60 мин) | `app.js:85` | → WAIT (в т.ч. NEAR→WAIT) | **Блокирует**; EXPIRED исключается кэшем |
| Shadow gap > 7 пп по выбранному исходу | `shadow/gate.js:34` | VALUE→NEAR | **Блокирует** |
| Shadow gap 5–7 пп и Confidence−штраф < 70 | `gate.js:37` | VALUE→NEAR | Условно |
| Shadow N/A | `gate.js:17` | гейт пропущен | **Fail-open** |
| DQ v2 (`scoreNormalized`) | `quality/dataQuality.js` | только диагностика | **Не блокирует** |
| Risk score, red flags, SOURCE_PARTIAL, MARKET_DISAGREEMENT | `risk/riskScore.js` | только диагностика/штраф к `decisionConfidenceV2` | **Не блокирует** |
| Sanity: prob≥0.9 при низком DQ, EV>100, edge>30, divergence>30пп, fair odds вне 1.1–20 | `model/sanityChecks.js` | предупреждения | **Не блокирует** |
| `decisionConfidenceV2` | `riskScore.js:108` | только диагностика | **Не блокирует** |
| Lineups/injuries | `riskScore.js:42` | INFO без штрафа | **Не блокирует** |
| Match confidence событий ≥ 0.7 | `oddsMatching.js:137`, `env.js:72` | отбор события | Блокирует на этапе матчинга |

Следствия:
- Все «умные» оценки качества (DQ v2, Risk, Confidence v2, Sanity) **не участвуют в решении**. Единственные независимые от модели защиты — STALE-рынок и Shadow gap.
- Публикуемая «Confidence» — это формула из `classify.js`, а не `decisionConfidenceV2`.
- `official-signals` создаётся для любой записи с `category === "value"` (`history.js:197`); sanity-предупреждения на выпуск не влияют.

## 2. Ранжированный список проблем

Формат: класс · файл · причина · последствия · способ исправления · тесты · риски · критерии успеха. Все пункты, затрагивающие защищённую логику (модель, пороги, VALUE-решение, Edge/EV, Confidence), требуют **вашего разрешения** до реализации.

### P1 [ФАКТ-КОД] Не сохраняются отклонённые решения и причины гейтов (нарушает требование «сохранять все отклонённые сигналы»)
- Файлы: `src/storage/history.js:102` (`appendSignals` пишет только value/near), `src/app.js:386-415` (snapshot анализа без кандидатов/причин), `app.js:329` (`shadowGate` лежит только в памяти).
- Что теряется: для WAIT/REJECTED/NO_MARKET нет вероятностей и коэффициентов; для VALUE→NEAR по Shadow gate причина и величина расхождения не сохраняются (`reason` не пишется); sanity-предупреждения есть лишь в `analyses`, без привязки к исходу.
- `shadow-signals.jsonl` содержит все три исхода, но только при наличии рынка и `shadowStatus OK`, без причин.
- Последствие: нельзя посчитать, сколько и каких ставок отсекают гейты и были ли они правы — это блокирует проверку почти всех остальных пунктов.
- Исправление (аддитивное, без изменения решений): новый append-only файл `decisions.jsonl`: на каждую пару (анализ, матч) — вероятности Production/Challenger, все 3 кандидата (odds, edge, EV), результат каждого гейта (pass/fail/N/A + значения), финальная категория, причина, ссылки на источник и свежесть рынка.
- Тесты: паритет — категории до/после на одинаковых входах идентичны; идемпотентность; запись при NO_MARKET; отсутствие секретов.
- Риск: рост размера файла (оценить ~1–2 КБ/матч), ошибка записи не должна ломать цикл (non-fatal).
- Критерий: 100 % матчей анализа имеют запись решения; причина любого не-VALUE восстановима.

### P2 [ФАКТ-КОД] Решение принимается по legacy-метрикам, расширенные проверки только советуют
- Файлы: `classify.js:5`, `app.js:296-345`, `sanityChecks.js`.
- Причина: DQ v2/Risk/Sanity вычисляются **после** классификации и не возвращаются в неё.
- Последствие: сигнал с `EV>100`, `edge>30` или расхождением с рынком >30 пп получает VALUE и официальную блокировку, если Shadow gap ≤ 7 пп (то есть при согласии двух моделей, имеющих общую слабость).
- Способ: **сначала измерить** (инструмент, раздел `gateCounterfactual`) ROI/калибровку выпущенных сигналов, которые сработали бы на каждый гейт. Только если по ним есть статистически значимое ухудшение — предложить владельцу сделать конкретные sanity-проверки обязательными блокировками (VALUE→NEAR, с записью причины, не удаление сигнала).
- Тесты: фикстуры реальных (не синтетических) записей из `official-signals` для каждого гейта; паритет на остальных.
- Риск: сокращение числа VALUE — не недостаток, но решение защищённое → разрешение владельца; не подбирать порог по ROI на малой выборке (переобучение).
- Критерий: гейт включается только при предварительно заданном критерии (см. §6).

### P3 [ФАКТ-КОД] «Confidence» — функция Edge, а не независимая оценка уверенности
- Файл: `classify.js:41`, дубль в `shadow/comparison.js:63`.
- Формула: `min(88, DQ·0.55 + max(0,Edge)·2.4 + 18)`. Чем сильнее модель расходится с рынком, тем выше «уверенность».
- Арифметика порога Confidence ≥ 70: нужный Edge = (52 − 0.55·DQ)/2.4 → DQ 65: 6.77 пп; 70: 5.63; 75: 4.48; 82: 2.87. Значит при minEdge = 4 условие Confidence **фактически является скрытым порогом Edge ≈ 4.5–6.8 пп** и не добавляет информации. При DQ ≥ 77 оно не связывает вообще.
- Последствие: Telegram показывает «Confidence», который растёт с вероятной ошибкой модели; пользователь может прочесть его как надёжность.
- Способ: не менять порог; переименовать/пояснить в UI (безопасно после одобрения) либо в V2H оценивать альтернативу без Edge в формуле. Это решение защищённое.
- Тесты: тест фиксирует таблицу «минимальный Edge для Confidence 70 по DQ».
- Критерий: UI не вводит в заблуждение; решение не меняется без разрешения.

### P4 [ФАКТ-КОД + ГИПОТЕЗА] Математика экстремальных вероятностей Production 1X2
Факты о формуле (`model/probability.js:56-67`):
`s = 0.65·ΔPPG + 0.22·ΔGD/игру + 0.75·Δform`; логиты `(0.28+s, 0.05−0.28|s|, −s)`.
- Три признака сильно коррелированы (очки, разница мячей и форма из одних и тех же матчей), веса заданы вручную, **без подгонки и без поправки малой выборки** (в отличие от challenger с `shrinkRate`).
- Разрыв логитов «победа − ничья» растёт как `0.23+1.28|s|`, т.е. ничья вымывается быстрее, чем у стандартной модели «сила + порог ничьей».
- Допуск модели: `DQ ≥ 65` достигается при ≥4 сыгранных матчах (3 игры → DQ 63 → WAIT; 4 → 65.8), то есть расчёт идёт по 4-матчевым сырым средним.
- Таблица перевода (прямой расчёт формулы):

| s | P(П1) | P(X) | P(П2) |
|---|---|---|---|
| 0 | 0.392 | 0.312 | 0.296 |
| 1.0 | 0.756 | 0.167 | 0.077 |
| 1.5 | 0.866 | 0.101 | 0.033 |
| 2.0 | 0.930 | 0.057 | 0.013 |
| 2.5 | 0.964 | 0.031 | 0.005 |

Примеры входов (расчёт по формуле): ΔPPG=1, ΔGD=1, Δform=0.4 → s=1.17; ΔPPG=1.5, ΔGD=1.5, Δform=0.6 → s=1.76; ΔPPG=2, ΔGD=2, Δform=0.8 → s=2.34.

- Экстремум >0.95 требует очень больших разрывов (сильнейший vs слабейший, особенно на малой выборке). **Как часто это встречается в реальных матчах и насколько это перекалибровано — неизвестно (ГИПОТЕЗА).**
- Косвенный факт: у challenger температурная калибровка T=1.175 (`shadow/comparison.js:6`) — т.е. сырые вероятности challenger были признаны избыточно уверенными на реальной выборке (сама выборка в репозитории отсутствует).
- Проверка на реальных данных: `forecastQuality` инструмента (ECE по корзинам, доля ≥0.8/0.9 и их фактическая точность с доверительным интервалом, средняя предсказанная vs фактическая доля ничьих) и существующий `npm run backtest:real` на Termux.
- Способ (только после данных и разрешения): shadow-проверка (а) усадки сезонных средних к лиге по числу игр, (б) подгонки температуры/весов walk-forward. **Не** вводить произвольный минимум ничьей.
- Критерий: улучшение LogLoss/ECE в walk-forward **и** отсутствие ухудшения калибровки выбранной стороны; сам по себе Brier/LogLoss не доказывает доходность (см. §6).

### P5 [ФАКТ-КОД] Shadow gate — единственная защита от общей ошибки, и он fail-open
- Файл: `shadow/gate.js:17`; сравнение только по выбранной стороне; пороги 5/7 пп из env.
- Если challenger недоступен — гейт «N/A», категория не меняется. Production и challenger используют одни и те же данные (таблица, матчи): гейт ловит расхождение моделей, а не ошибку данных.
- Не персистится (P1). 
- Способ: записывать результат гейта; решение о fail-closed при N/A — владельцу (после оценки, как часто N/A на VALUE-кандидатах).
- Критерий: в истории видны случаи gate N/A у выпущенных сигналов (инструмент: `SHADOW_UNAVAILABLE`).

### P6 [ГИПОТЕЗА, проверяема] Смещение отбора «лучший из трёх Edge» + выбор одного букмекера
- Файлы: `classify.js:28` (сортировка трёх Edge), `oddsMatching.js:157-183` (`bestH2H`: строка с наибольшей суммой коэффициентов, TODO «market consensus»).
- Максимум из трёх шумных оценок смещён вверх; при завышенной вероятности модели он выбирает «ошибочный» исход. Одна строка букмекера без сверки с консенсусом: выброс/устаревшая котировка пройдёт, если не STALE (рыночный разброс — только флаг LOW).
- Проверка: `calibrationOfSelectedSide` (средняя вероятность модели vs фактическая частота выигрышей среди выпущенных) и ROI по корзинам Edge/вероятности.
- Способ: V2H-вариант политики с консенсусной ценой (медиана no-vig по ≥3 книгам, лучшая цена только для исполнения).
- Защищённо (Edge/EV вход) → разрешение владельца.

### P7 [ФАКТ-КОД] Семантика блокировки сигнала
- `history.js:197-232`: официальный сигнал фиксируется при **первом** появлении VALUE и неизменяем; последующее понижение лишь пишет `DOWNGRADED`.
- Следствие: сигнал, который система сама через 30 мин понизила (например, Shadow gap), остаётся в ROI/статистике. Это соответствует политике иммутабельности, но искажает оценку качества гейтов.
- Способ: ничего не менять в выпуске; в аналитике разделять «выпущен и позже понижен» (события `DOWNGRADED`) и «стабильный VALUE». Данные для этого есть в `signal-events.jsonl`; расширить инструмент после первого прогона.

### P8 [ФАКТ-КОД, низкий приоритет] Несоответствия в диагностических метриках
- `riskScore.js:19` `modelAgreement` сравнивает два члена одной формулы — это не согласие моделей (Consensus не реализован).
- `app.js:303` `marketQuality = oddsEvent ? 100 : 0` не учитывает STALE/источник/match confidence.
- `dataQuality.js`: `squadCoverage` N/A считается нулём, `xgCoverage` N/A исключается; `sanityChecks` сравнивает DQ v2 (нормированный) с порогом legacy-шкалы.
- Всё это только диагностика; влияет на `decisionConfidenceV2` и доверие к отчётам. Менять после решения по P2.

### P9 [ФАКТ-КОД, низкий приоритет] Прочее
- `src/bot.js`: дубль `similarity/findOddsEvent/bestH2H` (символьное сходство >0.58, без окна по времени). Не точка входа `npm start`; требуется подтвердить, что мёртвый код (на Termux тоже), затем удалить/заменить на общий матчер. Безопасно, без влияния на модель.
- `challenger/teamStrength.js`: отсутствующий счёт трактуется как 0 (`|| 0`); безопасно, пока контекст содержит только FINISHED (football-data так и фильтрует); добавить защитный тест.
- Начало сезона: если у лиги нет ни одного сыгранного матча, `football-data` берёт матчи прошлого сезона; при 0 сыгранных в таблице legacy DQ = 66 (≥65): модель может выдать вероятности, опираясь только на форму прошлого сезона. Влияет лишь на 1-й тур; проверить частоту по `analyses`.

## 3. Что можно проверить независимо, а что реально способно улучшить сигналы

| Изменение | Проверяется независимо? | Может улучшить качество сигналов? |
|---|---|---|
| P1 персист решений/причин | Да (паритет + тесты) | Само по себе нет; **необходимое условие** оценки всего остального |
| P9 удаление мёртвого кода, защитные тесты | Да | Нет (гигиена) |
| P8 исправление диагностик | Да (юнит-тесты) | Косвенно (честность метрик) |
| P2 обязательные sanity-блокировки | Только на накопленных реальных сигналах; вероятно мало наблюдений | Возможно, только если контрфактуал покажет ухудшение |
| P3 Confidence | Формула проверяется алгебраически | UI/интерпретация, не доходность |
| P4 усадка/калибровка Production | Walk-forward на истории football-data без рынка: LogLoss/ECE | Улучшает калибровку; доходность — только через shadow-ставки и CLV |
| P6 консенсусная цена | Да по сохранённым котировкам, если пишутся все книги | Потенциально; нужен CLV |

Ограничение, которое надо принять заранее: при типичном стандартном отклонении ROI одной ставки ≈1.5 для обнаружения реального +5 % на уровне ~2σ нужно ≈ (2·1.5/0.05)² ≈ **3 600 ставок**. Поэтому ROI на сотнях ставок — **не** основание ни для включения гейта, ни для его отмены; основные ранние критерии — калибровка выбранной стороны и CLV, ROI — контрольный.

## 5. Подтверждение причин на реальных прогнозах — что и как

1. Передать на Termux архив, выполнить `node fvm-readonly-audit/audit.mjs --data <data> --out ~/fvm_audit_report.json`, прислать JSON (агрегаты, без секретов).
2. Отдельно `npm run backtest:real` (уже есть в репозитории; для 5 лиг одного сезона): секции «>=80/>=90», «top causes of extreme wrong predictions», ECE — это прямая проверка P4. Он пишет в `data/backtests`, поэтому запускать владельцу по своему усмотрению.
3. Правило интерпретации заранее: P4 подтверждается, если для вероятностей ≥0.8 фактическая частота (95 % ДИ Уилсона) ниже предсказанной средней; опровергается, если ДИ её содержит. При n<30 — «не интерпретируемо».

## 6. Архитектура V2H Decision Shadow (проект)

Допущение: V2H в репозитории не определён; ниже — проект теневого слоя, проверяющего **реальные ставочные решения** (а не только вероятности) на **одних и тех же замороженных предматчевых данных**.

**Принципы.** Не влияет на Production, Telegram, official signals, настройки; ошибки не фатальны (как существующий shadow-движок); пишет только в `data/v2h/` (append-only); включается флагом; никаких данных после `kickoff`.

**Компоненты**
1. **Snapshot freezer** — на каждый анализ и матч записывает неизменяемый снимок: хэш контекста (таблица+матчи ≤ kickoff), **все** котировки всех книг с `observedAt`, статусы провайдеров, версию кода/конфига.
2. **Policy registry** — чистые функции `snapshot → decision`. `P0` = точная реплика Production (импортирует тот же `classify`+гейты). Варианты: `P1` обязательные sanity-блокировки; `P2` консенсусная цена; `P3` усадка/калибровка вероятностей; `P4` комбинации. Каждая политика выдаёт полный след: 3 кандидата, результат каждого гейта, категорию, причину.
3. **Parity harness** — перепрогон `P0` на сохранённых снимках обязан воспроизвести категорию Production на 100 %; любое расхождение — баг до начала сравнения.
4. **Virtual ledger** — для каждой пары (политика, матч, исход) виртуальная ставка 1u по цене политики; расчёт тем же `settlement.js`, CLV тем же `clv.js` по закрывающей котировке.
5. **Evaluator** — парное сравнение на общих матчах: CLV (основной), калибровка выбранной стороны, LogLoss вероятностей, ROI с ДИ (контрольный), ROI **отклонённых** ставок (чтобы видеть, не отсекают ли гейты прибыльные), стратификация по лиге/сроку до матча/источнику рынка.
6. **Отчёт** — сводка раз в сутки в файл (без Telegram) до решения владельца.

**Критерии (фиксируются до запуска, чтобы не подгонять):**
- Минимум решений на политику и гейт: не менее 300 settled для калибровки/CLV; выводы по ROI — только с 95 % ДИ и с оговоркой §3.
- Число сравниваемых политик ограничено (≤5) из-за множественных сравнений.
- Продвижение политики в Production — только решением владельца, никогда автоматически.
- Если P0 расходится с Production (§3.3) — сравнение недействительно.
