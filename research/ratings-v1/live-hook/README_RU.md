# Подключение ratings-v1 к живому циклу как Shadow-наблюдателя — инструкция (НЕ применено к Termux)

Что добавляется в рабочий код: **5 строк в `src/app.js`** (импорт, константа с путём файла, защищённый вызов) и 1 новый файл `src/shadow/ratings/ratingsObserver.js` (+ ранее добавленные файлы модуля). Остальные файлы Termux не меняются.

## Что делает наблюдатель
- Раз за цикл, после блока Shadow V3 (когда `state.results` и `completedHistory` уже готовы), берёт **те же** объекты, строит состояние рейтингов по завершённым матчам (результат считается известным через 180 минут после старта и не позже `storedAt`) и дописывает по одному прогнозу на предстоящий матч поддерживаемой лиги (PL, PD, SA, BL1, FL1, DED, PPL, ELC, BSA) в **отдельный** файл `data/statistics/ratings-v1-shadow.jsonl`.
- Ничего не присваивает в `state`, не меняет `results`, категории, сигналы VALUE/NEAR, Telegram, статистику; ничего не `await`-ит; все ошибки перехватываются внутри и ещё раз снаружи (`try{…}catch{}`).
- Запись только в конец файла, по ключу матча `kickoff|home|away|ratings-v1`: уже записанная строка никогда не переписывается и не дублируется; прогноз записывается только пока `kickoff > storedAt`.

## Включение и отключение
| Действие | Как |
|---|---|
| Включить | переменная окружения `RATINGS_V1_SHADOW=1` (`true`/`yes`) при запуске процесса. По умолчанию **выключено**. `.env` я не трогаю — задайте переменную там, где вы запускаете бота |
| Выключить без перезапуска | создать пустой файл `data/statistics/ratings-v1.DISABLED` (проверяется каждый цикл); удалить файл — включится снова |
| Выключить полностью | убрать переменную и перезапустить, либо откатить патч |

## Безопасное применение поверх незакоммиченных изменений Termux
Выполнять в корне рабочего дерева Termux; все шаги кроме 5–7 только читают.
1. `git fetch origin claude/termux-ratings-v1-live-hook`
2. Добавить только новые файлы (существующие не затрагиваются):
   `git diff e7e133c origin/claude/termux-ratings-v1-live-hook -- src/shadow/ratings scripts test > /tmp/ratings-v1-files.diff && git apply --check /tmp/ratings-v1-files.diff && git apply /tmp/ratings-v1-files.diff`
   (если `src/shadow/ratings` уже есть из предыдущей ветки, `git apply --check` сообщит конфликт — тогда достаточно скопировать `ratingsObserver.js`, `ratingsShadow.js`, `scripts/apply-ratings-v1-hook.mjs` и два тестовых файла).
3. Сухой прогон вставки: `node scripts/apply-ratings-v1-hook.mjs src/app.js` — печатает, что будет добавлено, **ничего не пишет**. Если якорь не найден (в вашем `app.js` изменён блок Shadow V3), скрипт прервётся и выведет три фрагмента для ручной вставки.
4. Тесты: `node --test test/ratingsV1.test.js test/ratingsV1Observer.test.js`, затем `npm test` (ожидается ваш прежний результат; на чистом `termux-v0.5` с патчем у меня 440 из 443 — те же 3 теста `Doctor`).
5. Вставка: `node scripts/apply-ratings-v1-hook.mjs src/app.js --write` (создаёт резервную копию `src/app.js.bak-ratings-v1`). Альтернатива, если дерево совпадает с `e7e133c`: `git apply research/ratings-v1/live-hook/ratings-v1-live-hook.patch`.
6. `node --check src/app.js`; запуск **без** флага — поведение прежнее (наблюдатель сразу возвращает `DISABLED`).
7. Включение: запуск с `RATINGS_V1_SHADOW=1`; после первого цикла убедиться, что появился `data/statistics/ratings-v1-shadow.jsonl` и что строки имеют `createdAt < kickoff`.

Откат: удалить 5 добавленных строк (все содержат метку `ratings-v1 observer`; можно `grep -v "ratings-v1 observer" src/app.js`) или вернуть `src/app.js.bak-ratings-v1`; файл прогнозов можно оставить (он не используется Production) либо удалить по вашему решению.

## Что проверено тестами
- Production-вывод побайтно одинаков при включённом и выключенном наблюдателе: результаты `analyseFixture`, статистика Shadow и файлы `dual-shadow.jsonl`/`predictions.jsonl` (тест воспроизводит хвост цикла с реальными функциями).
- Входные объекты полностью заморожены (`Object.freeze`) — наблюдатель их не изменяет; хеш входов до и после совпадает.
- Нет утечки: результат, ставший известным позже момента `storedAt`, и матч в будущем не влияют на записанный прогноз; изменение результата, который был известен, влияет (проверка самого теста).
- Идемпотентность: повторный вызов не пишет; следующий цикл добавляет только новые матчи, ранее записанные строки побайтно неизменны.
- Отказоустойчивость: сломанная история, `null`, неверная дата, недоступный путь, падающий логгер — исключение не выходит наружу.
- Вставка в `app.js`: три якорные вставки, идемпотентность, обратимость (после удаления помеченных строк файл совпадает с исходным побайтно), корректный синтаксис (`node --check`), вызов не содержит присваиваний `state` и `await`, расположен после блока V3 и до телеметрии, передаёт именно объекты цикла и корректно читает значения флага; даже падающий наблюдатель не выходит за пределы `try/catch`.
- Импорт: ни один производственный модуль не импортирует код `shadow/ratings`, кроме `app.js` (наблюдатель).

## Совместимость с существующими Shadow и локальными правками
- Существующие Shadow (Challenger, V2H, BASE k=0 / CANDIDATE k=8, V3) не затрагиваются; `ratings-v1` пишет в свой файл с тем же ключом матча (`kickoff|home|away`), поэтому с ними сопоставляется без дублирования.
- Вставка привязана к якорям: строка импорта `v3History`, константа `V3_SHADOW_HISTORY_FILE` и блок `try{…updateV3ShadowHistory…}catch`. Если ваши незакоммиченные правки не трогают эти три места, применяется как есть; иначе скрипт ничего не изменит и подскажет ручную вставку.

## Что делать с прогнозами
Файл прогнозов сопоставляется с `dual-shadow.jsonl` по `snapshotKey` без суффикса `|ratings-v1`/`|dual-shadow-v1`; сравнение с Production, Challenger, k=8 и рынком — `research/ratings-v1/compare_ratings_v1.py` (потребует небольшой адаптации чтения живого файла вместо бэктеста). Решения по VALUE на основе `ratings-v1` не принимаются без отдельного разрешения.
